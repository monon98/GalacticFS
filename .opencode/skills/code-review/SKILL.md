# 代码审查

## 什么时候用

- 完成一个功能或修复后，自查自己的改动
- 合并前审查他人/代理产生的代码改动

## 审查流程

1. **先看改动范围**：用 `git diff` 或 `git status` 确认改了哪些文件，排除无关文件（格式化噪音、误提交）
2. **按以下清单逐项检查**：

### 正确性

- 边界条件：空目录、超大文件树、文件已删除/移动、权限拒绝
- IPC 数据校验：渲染进程传来的路径/参数不可信，主进程必须校验
- 异步处理：未 await 的 Promise、竞态条件、缩略图/扫描任务的取消与清理

### 安全与架构

- 渲染进程未直接访问文件系统或 Node API（必须走 contextBridge）
- 没有引入删除/移动/重命名等破坏性功能（GalacticFS 是只读浏览器，`docs/GalacticFS.md` §2.4 明确排除）
- 没有硬编码密钥/路径；主进程文件操作限制在配置允许的根目录内

### 性能（本项目有海量文件场景）

- 扫描/缩略图是否阻塞主进程或 UI（应异步 + 进度反馈）
- 3D 场景是否会用 InstancedMesh/LOD（文档 §7.1：≥30 FPS）
- 避免渲染进程无谓重渲染（React key、memo、useMemo）

### 风格与一致性

- Prettier 风格：无分号、单引号、printWidth 100、无尾逗号
- **中文注释齐全**：模块顶部职责说明、公共 API 参数/返回/异常、复杂逻辑的"为什么"、测试意图；无冗余/死注释
- 命名与既有模块一致；文档片段已按仓库 TS 风格改写

### 验证

- `pnpm typecheck`、`pnpm lint` 是否通过
- 是否有对应测试或至少手动验证路径（`pnpm dev`）

## 输出格式

按严重程度列出问题清单：

- **P0（必须修）**：功能错误、安全问题、架构违规
- **P1（应该修）**：边界条件缺失、性能风险
- **P2（建议）**：风格、命名、小改进

每条给出行号引用（`文件:行号`）和具体修改建议。全部通过时明确说明"通过"。
